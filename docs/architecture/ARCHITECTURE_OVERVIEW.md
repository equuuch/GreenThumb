# ARCHITECTURE_OVERVIEW.md

Высокоуровневая архитектура проекта GreenThumb, обоснование выбора паттернов проектирования и логика взаимодействия компонентов системы.

## 1. Архитектурный паттерн: Service Layer

В проекте реализовано четкое разделение ответственности между слоем хранения данных, бизнес-логикой и слоем представления:

* **Data Access Layer (DAL)**: использование SQLAlchemy 2.0 для изоляции SQL-запросов и обеспечения типобезопасности. Подключение к SQLite настроено с параметром `check_same_thread=False` для стабильной работы в многопоточной среде Flet.
* **Business Logic Layer (BLL)**: вынос всей логики в независимые сервисы (Auth, Plant, Care, AI). Это позволяет тестировать бэкенд без участия интерфейса и гарантирует транзакционную целостность через блоки `try-except-rollback`.
* **Presentation Layer**: реактивный интерфейс на Flet, который является «тонким клиентом». UI только отображает данные, полученные из сервисов, и не содержит логики обработки данных.

## 2. Стратегия управления данными

Система спроектирована по принципу Offline-First для обеспечения стабильной работы без интернета:

* **SQLite**: выбор в пользу встраиваемой базы данных позволяет хранить всю информацию локально на устройстве пользователя.
* **Нормализация справочника**: разделение пользовательских данных (`plants`) и глобального каталога (`plant_catalog`) исключает дублирование эталонной информации о видах.
* **Система алиасов**: таблица `plant_aliases` позволяет сопоставлять народные названия с научными, обеспечивая быстрый локальный поиск без обращения к ИИ.

## 3. Работа с медиа и файлами

Логика хранения изображений оптимизирована для мобильных устройств и интеграции с Flet:

* **File Service**: физическое сохранение фотографий в папку `assets/`. Имена файлов генерируются через `uuid4` для исключения конфликтов.
* **Относительные пути**: в базе данных хранятся пути без префикса `assets/` (например, `plants/uuid.jpg`). Это позволяет Flet автоматически подтягивать изображения, используя встроенный механизм поиска ассетов.
* **Image Processing**: автоматическое приведение всех фото к формату JPEG с качеством 70% и ресайзом до 1024px.

## 4. Система автоматизированного планирования

Реализован механизм «Бесконечного цикла ухода», который минимизирует когнитивную нагрузку на пользователя:

* **Grid-based planning**: создание сетки задач в календаре происходит не по одной, а пакетом на 30 дней вперед.
* **Динамический пересчет**: при выполнении задачи («полив сделан») система удаляет все будущие невыполненные задачи и заново генерирует график, отталкиваясь от новой фактической даты.
* **Адаптивные интервалы**: расчет дат производится на основе метаданных из каталога, которые могут быть уточнены индивидуально для каждого растения через поле `user_light_level`.

## 5. Интеллектуальный модуль

Логика взаимодействия с GigaChat API построена на принципе максимальной экономической эффективности:

* **Оркестрация моделей**: автоматическое переключение между моделью Lite для текстовой генерации и моделью Max для анализа фотографий.
* **Кэширование токенов**: хранение JWT в памяти процесса на 30 минут с защитным интервалом для минимизации лишних сетевых запросов на авторизацию.
* **Аудит ресурсов**: логирование каждого запроса и ответа ИИ для контроля расхода токенов и возможности восстановления контекста консультации.

## 6. Генерация отчетности

* **Независимый рендеринг**: прямой программный рендеринг PDF-документов через ReportLab без использования браузерных движков.
* **Аналитическое ядро**: автоматический расчет «Дисциплины ухода» на основе соотношения выполненных и пропущенных задач в календаре.

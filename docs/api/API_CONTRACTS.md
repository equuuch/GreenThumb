# Спецификация межслойного взаимодействия

Настоящий документ определяет архитектурный стандарт взаимодействия между интерфейсным слоем (UI) и слоем бизнес-логики (Services) проекта GreenThumb

## 1. Архитектурный стандарт ответа

Все методы бизнес-логики следуют унифицированному стандарту возврата данных в виде кортежа

```python
data_object, error_message = ServiceName.method_name(db_session, **params)
```

* **Data_object**: экземпляр модели SQLAlchemy, список объектов, словарь или строка. если операция завершилась ошибкой, всегда возвращается None
* **Error_message**: строковая переменная, содержащая текст ошибки на русском языке. если операция успешна, возвращается None
* **Логика применения**: если error_message не пуст, интерфейс обязан отобразить текст ошибки пользователю (рекомендуется ft.SnackBar)

## 2. Спецификация модулей и методов

### 2.1. Управление доступом (AuthService)

* **register_user(db, email, password, name)**
    * **Вход**: почта (нормализуется в lower), пароль (мин. 6 символов), имя
    * **Результат**: объект User
* **authenticate_user(db, email, password)**
    * **Результат**: объект User при успехе, иначе None

### 2.2. Интеллектуальный помощник (GigaChatService)

* **get_passport_data(db, user_id, name)**
    * **Назначение**: генерация технических характеристик растения по его названию
    * **Структура результата**: словарь с техническими параметрами для справочника
* **identify_plant_photo(db, user_id, img_bytes)**
    * **Назначение**: распознавание вида растения по фотографии для последующего подтверждения
* **diagnose_plant(db, user_id, img_bytes)**
    * **Выход**: текстовый протокол с описанием болезни и планом лечения
* **ask_agronomist(db, user_id, plant_info, query)**
    * **Назначение**: консультация в формате чата на основе контекста растения

### 2.3. Реестр растений (PlantService)

* **confirm_and_create_plant(db, user_id, catalog_data, custom_name, image_bytes)**
    * **Логика**: сохраняет фото на диск, вносит вид в справочник (если он новый) и создает запись в базе
* **get_or_create_catalog_item(db, ai_service, user_id, query)**
    * **Логика**: умный поиск, который автоматически расширяет справочник через ИИ, если растение не найдено
* **add_measurement(db, plant_id, height, note, image_bytes)**
    * **Вход**: числовое значение роста, заметка, опциональное фото прогресса
* **archive_plant(db, plant_id, reason)**
    * **Логика**: перевод растения в неактивный статус и удаление будущих задач в календаре
* **delete_plant_permanently(db, plant_id)**
    * **Логика**: безвозвратное удаление записи из бд и физическое стирание фотографии с диска

### 2.4. Планировщик ухода (CareService)

* **get_today_tasks(db, user_id)**
    * **Выход**: список задач, у которых плановая дата меньше или равна текущей
* **complete_task(db, task_id)**
    * **Логика**: закрытие текущей задачи и автоматическое создание новой через интервал из справочника

### 2.5. Генератор отчетности (ExportService)

* **create_plant_pdf(data)**
    * **Вход**: нормализованный словарь данных от сервиса отчетов
    * **Результат**: относительный путь к созданному файлу в папке ресурсов

## 3. Технические регламенты реализации

* **Оптимизация изображений**: интерфейс обязан использовать файловый сервис для обработки фото перед отправкой в ии для экономии ресурсов
* **Работа с сессиями**: вызов любого метода сервиса должен происходить внутри контекстного менеджера с получением сессии из фабрики
* **Доступ к файлам**: пути к фотографиям хранятся относительно папки загрузок. в интерфейсе необходимо использовать префикс папки ресурсов
* **Навигация**: все переходы между экранами осуществляются синхронно через встроенный механизм маршрутизации фреймворка

# Спецификация межслойного взаимодействия (Service Layer API)

Настоящий документ определяет архитектурный стандарт взаимодействия между интерфейсным слоем (UI) и слоем бизнес-логики (Services) проекта GreenThumb

## 1. Архитектурный стандарт ответа (Result-Error Tuple)

Все методы бизнес-логики следуют унифицированному стандарту возврата данных для обеспечения централизованной обработки ошибок

```python
data_object, error_message = ServiceName.method_name(db_session, **params)
```

* **Data_object**: экземпляр модели SQLAlchemy, список объектов (list), словарь (dict) или строка. если операция завершилась ошибкой, всегда возвращается None
* **Error_message**: строковая переменная, содержащая текст ошибки на русском языке. если операция успешна, возвращается None
* **Логика применения**: если error_message не пуст, интерфейс должен прервать текущий сценарий и отобразить текст ошибки (рекомендуется ft.SnackBar)

## 2. Спецификация модулей и методов

### 2.1. Управление доступом (AuthService)

* **register_user(db, email, password, name)**
    * **Вход**: почта (нормализуется в lower), пароль (мин. 6 символов), имя
    * **Результат**: объект User
* **authenticate_user(db, email, password)**
    * **Результат**: объект User при успехе, иначе None

### 2.2. Интеллектуальный помощник (GigaChatService)

Методы, помеченные как JSON, возвращают объект dict, требующий десериализации

* **get_passport_data(db, user_id, name) [JSON]**
    * **Структура ответа**:
    ```json
    {
      "species_name": "название",
      "latin_name": "latin",
      "description": "описание до 200 знаков",
      "watering_interval": 7,
      "light_level": 0.8
    }
    ```
* **identify_plant_photo(db, user_id, img_bytes) [JSON]**
    * **Назначение**: автоматическое определение вида по фото для первичной регистрации
* **diagnose_plant(db, user_id, img_bytes) [Text]**
    * **Выход**: развернутый текстовый протокол лечения и рекомендации
* **ask_agronomist(db, user_id, plant_info, query) [Text]**
    * **Назначение**: оперативная консультация садовода в формате чата

### 2.3. Реестр растений (PlantService)

* **create_user_plant(db, user_id, catalog_id, custom_name, image_bytes)**
    * **Логика**: сохраняет фото на диск, создает запись в бд и автоматически генерирует первую задачу в CareCalendar
* **get_user_plants(db, user_id)**
    * **Выход**: список объектов Plant, содержащих custom_name, image_url и status_text

### 2.4. Цикл ухода (CareService)

* **get_today_tasks(db, user_id)**
    * **Выход**: невыполненные задачи, где scheduled_date меньше или равна текущей дате
* **complete_task(db, task_id)**
    * **Логика**: помечает задачу как выполненную и создает следующую, прибавляя интервал полива из справочника

### 2.5. Мониторинг роста (GrowthService)

* **add_measurement(db, plant_id, height, note, image_bytes)**
    * **Вход**: числовое значение роста, текстовая заметка, опциональные байты фотографии

### 2.6. Генератор отчетности (ExportService)

* **create_plant_pdf(data)**
    * **Вход**: нормализованный словарь, полученный от ReportService
    * **Результат**: относительный путь к созданному файлу в папке assets/reports/

## 3. Технические регламенты реализации

### Оптимизация медиа

Интерфейс обязан прогонять любые изображения через FileService.process_and_save перед их отправкой в методы ии (ресайз до 1024px)

### Управление сессиями

Вызов сервисов должен происходить строго внутри контекстного менеджера:
```python
with next(get_db()) as db:
    data, err = AuthService.authenticate_user(db, email, password)
```

### Пути к файлам

База данных хранит относительные пути. Для корректного отображения необходимо использовать префикс:
```python
f"uploads/{plant.image_url}"
```

### Навигация

Переходы между экранами реализуются синхронно через ft.use_context(RouteContext)
```python
route_context.navigate("/home")
```
